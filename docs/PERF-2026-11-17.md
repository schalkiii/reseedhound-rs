# 性能与延迟评估（2026-11-17 实机日志）

> 数据来源：本机 `deploy/logs/reseed.log`（release 实机）、`%TEMP%/sh_verify/logs/reseed.log`
> （debug CLI 单站点演练）、`deploy/gui-check/logs/reseed.log`（debug GUI 全量轮次），
> 以及对站点 API 的直接测量（curl，2026-11-17 22:00）。
> 结论以日志时间戳为准；debug 构建的 CPU 侧数字不代表 release。

## 1. 实测数字

| 环节 | 规模 | 耗时 | 备注 |
|---|---|---|---|
| 扫描本地种子 | 41,890 个 .torrent | **33 s**（GUI debug）/ **46 s**（CLI debug） | rayon 并行 + bencode；去重后剩 4,244 个待查 |
| CookieCloud 同步 | 1.0 MB 密文 / 86 站写回 | **≈1 s** | 解密与 YAML 回写都不是瓶颈 |
| 配置重读 | 每次 2 个小 YAML | 毫秒级 | 调度器每 5 s 一次，可忽略 |
| 站点查询（单站） | 4,244 个 hash，100/批 ≈ 43 批 | **≈65 s / 批**，见下 | 该站 TTFB 本身 5–12 s |

日志证据（`sh_verify`，只跑 `xiudaoyuan` 一个站）：

```
21:08:11 [阶段2] 查询站点: xiudaoyuan (4244 个种子)
21:09:24 请求成功 https://pt.1ctrl.cn/api/pieces-hash (第 1 次重试后恢复)
21:10:29 请求成功 ... (第 1 次重试后恢复)
21:11:34 请求成功 ... (第 1 次重试后恢复)
```

每 ~65 s 才推进 2 个批次，且**每个批次都走了一次重试**：请求先耗掉 `api_timeout=60s` 超时，
重试才拿到结果。按 43 批 × 65 s / 2 并发估算，单站全量查询需 **20–45 分钟**，
其中约 90% 时间花在“等超时”而不是真实计算。

## 2. 站点侧直接测量（同一接口，curl）

| 场景 | TTFB | 总耗时 |
|---|---|---|
| 1 个 hash | 6.8 s / 11.4 s（两次） | 同左 |
| 100 个 hash（串行两次） | 5.2 s / 5.3 s | 同左 |
| 4 个请求并发（各 100 hash） | 9.1 / 10.2 / 11.2 / 11.7 s | 全部 HTTP 200，无 429 |

结论：站点接口本身**慢但可用**（5–12 s），并不会稳定超过 60 s。因此 60 s 超时是引擎侧
“最坏情况兜底”被当成了常规路径；真实 hash 的冷查询/排队可能更慢，但当前日志无法区分
“站点慢”与“请求排队”。

## 3. 建议（按收益排序）

1. **`global.api_timeout` 60 → 15~20 秒**：配合 `retry_count=2`，单批最坏从 65 s 降到 ~20 s；
   站点若真超过 20 s，重试通常能命中其缓存（实测重试都能成功）。
2. **慢站单独降批**：`batch_size` 100 → 50 只对慢站生效（可在 sites.yaml 用 `download_interval`
   之外的字段扩展），批越小越容易在超时内完成。
3. **提高每站批并发 2 → 4**：实测 4 并发无 429，吞吐可再翻倍；注意别和 `global.concurrency`（20）
   叠加过量。
4. **可观测性**：已把“重试恢复”日志补上首次错误（`首次错误: timeout / HTTP 5xx`），下次跑一轮
   即可判断是超时还是被限流，再决定上面 1/3 的力度。
5. 本地扫描侧暂时不需要动：41,890 个种子 33 s（debug），release 走 LTO 后应明显更快；
   如要再压，可把 `scan_directory` 的 rayon 线程数固定为物理核数并复用 bencode 缓冲。

## 4. GUI 侧

- 站点设置页从「每站 3 行卡片」改为「单行紧凑表格 + 搜索筛选」：同高度下可见行数从 ~5 行
  提升到 ~14 行（960×680 窗口、debug 构建实测渲染无 panic）。
- 站点选择面板最多一次渲染 65 个 chip（enabled 站点），展开/收起无卡顿。
- 「本轮站点范围」只作用于下一轮（`on_report` 清空），定时轮次仍跑全部站点，避免误设后长期少跑。

## 5. 站点下载配额与 qB 落库的账目差（麒麟个案）

现象：麒麟（www.hdkyl.in）被提示超过每小时下载种子上限，但 qB 里没有辅出麒麟的种子。

事实核对（2026-11-17 本机全部日志）：

- `deploy/logs`、`deploy/gui-check/logs`、演练日志中**没有任何「阶段3/辅种成功/下载」记录**——
  Rust 版今天的轮次都停在阶段1/2 或引擎启动即失败，本次配额消耗不是 Rust 版造成的
  （更可能来自此前 Python 版或更早的运行，需查对应日志确认）。
- 配额计数点是 `download.php?id=…&passkey=…`：**每次请求都计数**，包括重试、包括返回
  错误页/死种页的请求。

我们引擎中「消耗配额但 qB 不入库」的四种路径：

| # | 路径 | 日志可见性（修复后） |
|---|---|---|
| 1 | 下载成功但不是有效 .torrent（HTML 错误页） | 有 warn：「下载的不是有效torrent文件」 |
| 2 | 下载成功但 qB 添加失败（认证/save_path/磁盘） | **此前完全静默**；现已补 warn：「添加失败（已消耗 XX 下载配额）」 |
| 3 | 下载超时重试：每次重试都再次请求 download.php | 超时有 debug，重试成功有 info |
| 4 | 阶段3进行中进程被终止 | 新增「终止本轮」后会在批次边界收尾并保留部分统计 |

去重保护（正常情况下重复轮次不会再下载）：`reseed_history`（pieces_hash+站点+id）与
`qb_info_hashes` 增量去重都会跳过已成功条目。

建议：用修复后的版本跑一轮（可先「演练模式」或只选麒麟），看是否出现「添加失败（已消耗
下载配额）」——出现则说明卡在 qB 添加侧；若完全没有下载记录而站点仍计数，则配额消耗来自
其它客户端/旧版工具。若麒麟限速严格，可再加「每站每轮下载上限」配置（暂未实现）。
